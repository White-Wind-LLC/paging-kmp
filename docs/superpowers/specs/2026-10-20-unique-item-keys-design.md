# Unique item keys for both pagers

**Date:** 2026-10-20
**Status:** draft
**Issue:** [#52](https://github.com/White-Wind-LLC/paging-kmp/issues/52) (source: YouTrack WMS-1905)

## Why

The WMS client wants to key its paged `LazyColumn`s by item id (WMS-1876: 51 mobile entity lists built
on `createRetryingStreamingPager`). Desktop tables want the same through `rowKey` in table-kmp, which
ends up in a `LazyColumn` key. With today's pagers that crashes.

`StreamingPager` builds its `PagingMap` from one independent stream per `loadSize` window, and every
portion is published as soon as it arrives. The backend changes data atomically; the client sees the
change window by window. Between two portions one item can sit at two positions:

```
delete above, only window 0..19 has updated
pos 18  T   (new)
pos 19  U   (new)
------- window boundary
pos 20  U   (stale)   <- same id twice: "Key U was already used"
pos 21  V   (stale)
```

The same happens on insert above (lower window first) and when a sort-field change moves an item
between windows. Between `preloadSize + closeThreshold` (streams closed) and `cacheSize` (values
still cached) nothing refreshes stale values, so a duplicate there lives until the user scrolls to it.

`Pager` has the same property over time: `CacheAccumulator.next` resets the cache only when
`totalSize` changes, so pages loaded before and after a backend change are merged unchecked.

A second trap: a consumer cannot compute the key through `PagingMap.get`, because it calls `onGet`.
`LazyColumn` computes keys for ~230 positions around the viewport (foundation 1.12.1), so the pager
would believe the user jumped far away and replan its window.

## Goals

1. A consumer can key a paged list by item id and never gets `Key … was already used`, with either
   pager.
2. A transient duplicate never appears on screen: a position whose item is already shown elsewhere
   looks like a position that is not loaded yet. A duplicate that is really in the source is shown
   (see "A duplicate that does not go away").
3. Reading keys does not move the pager's window.
4. Consumers that do not opt in see no change at all.

## Non-goals

- A consistent snapshot without gaps. That needs a protocol change (a revision on every portion and
  on `total`, or a single stream for the whole window) and is a separate server task.
- Restarting a single streamed window on demand (the original "option B" in the issue). Not needed:
  see "Why hidden positions recover" below.
- Migrating the WMS lists (WMS-1876) and table-kmp. They follow the release.

## Anti-goals

- A fallback key that can collide with a real key. Whatever the consumer's key type, including
  `Int`, two positions must never share a key.
- Each consumer having to know a trick (`values[i]` instead of `get`, `?: -(it + 1)`, …) to stay safe.
- A position that stays a placeholder forever while its data is in fact available.

## Decided

These were decided with the maintainer and are not up for the builder to change.

### API

- Both `Pager` and `StreamingPager` get an optional `itemKey: ((T) -> Any)? = null`, in the same
  release. It goes before the trailing `readData`/`readPortion` lambda so that trailing-lambda call
  sites keep compiling.
- `PagingMediatorConfig` gets the same `itemKey` and passes it to the `Pager` the mediator builds
  internally, otherwise mediator users cannot opt in (*my call*).
- `PagingMap` gets `keyAt(index: Int): Any`. It never returns `null` and never calls `onGet`.
  - Loaded, visible position: `itemKey(item)`.
  - Any other position (not loaded, hidden, out of range, or no `itemKey` configured): a fallback
    key generated by the library, a `String` with a reserved prefix, e.g. `"ua.wwind.paging#20"`.
    A `String` is storable in an Android `Bundle` and is never equal to an `Int`, `Long` or `Uuid`.
- Consumer usage:

  ```kotlin
  val pager = StreamingPager(..., itemKey = { it.id.value })

  LazyColumn {
      items(count = data.size, key = { data.keyAt(it) }) { index ->
          when (val entry = data[index]) { /* ... */ }   // onGet only here
      }
  }
  ```

- Keys, fallbacks included, are unique within one `PagingMap` only. Two pagers rendered into one
  `LazyColumn` are not supported and the KDoc of `keyAt` says so (*my call*: the use case is one
  pager per list).
- KDoc on `itemKey` states two requirements: the key must be storable in an Android `Bundle`
  (`Uuid`, `String`, a primitive; a boxed value class is not), and it must not be a `String` starting
  with the reserved prefix.
- `PagingMap.mapValues` and `PagingData.map` keep keys and hidden positions unchanged, so mapping in a
  ViewModel loses nothing.

### Conflict rule

- When the same key lands on two positions, the position written by the most recent portion wins.
  The other position loses.
- A losing position is **hidden** from the published `PagingMap`: absent from `values`, so `get`
  returns `EntryState.Loading` and `keyAt` returns the fallback key. This is always on when `itemKey`
  is set; there is no switch to show the duplicate instead.
- Hidden is not deleted. The pager keeps the losing value in its internal cache and tracks
  key → positions. When the winning position is overwritten by another item, or pruned, the key goes
  back to the position that still holds it and that position becomes visible again.
- The index is maintained wherever the cache changes: portion merge, `pruneToRange`, total-size
  change, `Pager.refresh`, and the `Pager` cache reset on a total change. Cost is proportional to the
  changed positions, not to the whole cache.

Same frames as above, with this design:

```
            internal   published    keyAt
pos 19      U          U            U
pos 20      U (stale)  (absent)     "ua.wwind.paging#20"   -> placeholder row
...window 20..39 arrives...
pos 20      V          V            V
```

### Why hidden positions recover

- Winner overwritten: the internal cache still holds the loser, so it reappears at once.
- Loser's window is still streaming: its next message replaces the stale value.
- Loser's window is no longer streaming, or (`Pager`) the page is not being reloaded: the hidden
  position is a hole in the published map. Both pagers compute `settledRange` and the missing ranges
  from the published map (`settledRangeAround`, `Pager.planLoad`), so reading the hole reaches the
  planner, which reopens the window or refetches the page.

The second and third points must be proven by tests, not assumed.

### A duplicate that does not go away

Hiding assumes the duplicate is stale data that a fresher read replaces. A source can also return the
same key at two positions in a consistent result (a join that duplicates rows, ties in an unstable
sort, an `itemKey` that is not unique). Then nothing replaces it: `Pager` would reload the two pages
in turn forever, each reload winning and hiding the other copy, and `StreamingPager` would keep a
placeholder for data it holds.

Decided: once a conflict is **confirmed**, both rows are shown. The losing position becomes visible
again with its value and keeps the fallback key, so keys stay unique and nothing crashes; the repeated
row is visible, which is the honest picture of a data error.

A conflict is confirmed when the losing position's own source has had its chance to correct it:

- `Pager`: the hidden position's page was refetched and still places the same key there. That
  refetch must not count as a new win that hides the other copy - no reload loop.
- `StreamingPager`: the losing position's window delivered a portion that still places the key
  there; or the window is live but stays silent for a bounded grace period after the conflict
  appeared (*my call; the builder picks the value, on the order of `keyDebounceMs`*); or the window
  was closed and reopening it brought the same value back.

A confirmed conflict ends like any other: when either position is overwritten with a different key,
or pruned. A later fresh conflict on the same key starts hidden again.

`StreamingPager` logs a warning once per confirmed conflict (it already has a logger). `Pager` has no
logger and does not get one for this (*my call*). KDoc on `itemKey` says the key should be unique in
the source and describes what a real duplicate looks like on screen.

### Cost accepted

- Instead of a duplicate row for a frame or two, a placeholder row for a frame or two.
- If the most recent portion is itself the stale one, the fresh row is hidden briefly instead of the
  stale one.

## Constraints

- Kotlin Multiplatform, `explicitApi()`. `StreamingPager` stays `@ExperimentalStreamingPagerApi`.
- Hot path: a live stream must not pay an O(cache) walk per message (see the existing
  `prunedCacheRange` and `mergeIntoCache` work). With `itemKey == null` the pagers must behave and
  cost exactly as today.
- Source compatibility: existing code constructing `PagingMap(size, values, onGet)`, calling
  `copy(values = …)`, `mapValues`, `PagingData.map` keeps compiling and behaving the same.
- New public API, so the release is a minor version: 2.4.0, with a `CHANGELOG.md` entry and a README
  section on id keys.
- Repo conventions: English, short comments that add missing context only.

## Left to the builder

- How `PagingMap` carries keys and the fallback (e.g. a parallel persistent map, or a nullable
  internal holder), and how `data class` equality/`copy` are kept sensible.
- Where the internal cache vs. the published view lives in each pager, and how `CacheAccumulator`
  and `StreamingPagerState.onPortion` share the conflict logic (a common internal helper is
  expected).
- The exact reserved prefix and its constant name.
- Whether `firstKey`/`lastKey` and similar helpers look at visible positions only (expected: yes,
  they read `values`).

## How to verify

Unit tests in `paging-core` (common):

1. `StreamingPager` with `itemKey`, two windows; the lower window's shifted portion arrives before the
   upper one. In every published `PagingMap`: no key returned by `keyAt` for two positions, no item
   with the same key visible twice in `values`; after both portions keys match positions and nothing
   is hidden.
2. Same scenario in the opposite order (insert above) and for an item moving between windows.
3. Winner overwritten → loser becomes visible again with its key.
4. Hidden position in a window whose stream is closed: reading it via `get` reopens the window and
   the position fills in.
5. `Pager` with `itemKey`: two pages with an overlapping item at the same `totalSize`; same
   uniqueness assertions; reading the hidden position triggers a reload of its page.
6. `keyAt` over 200+ positions calls no `onGet` and moves no window.
7. `itemKey` returning `Int`: fallback keys never equal a real key, including for unloaded positions
   whose index equals some item's id.
8. `mapValues` / `PagingData.map` preserve keys and hidden positions.
9. `itemKey == null`: existing test suites pass unchanged; `keyAt` returns fallback keys only.
10. Real duplicate, `Pager`: the source returns the same key on two pages consistently. After one
    refetch both rows are visible, keys stay unique, and no further loads are issued (no loop).
11. Real duplicate, `StreamingPager`: both windows live and silent → both rows visible after the
    grace period; loser's window re-emits the same value → visible at once; warning logged once.
12. `PagingMediator` with `itemKey`: a stale local portion followed by the remote one within one pass
    gives unique keys and settles to the remote data.

Live, together with WMS-1876: an id-keyed list with a window boundary on screen (rows ~15–25); delete
and create an item from another session. No crash, no duplicate row, rows move with animation.
